# Decision log: Look System and theme packs

Decisions made by the owner on 2026-11-03. **Decided means default direction, not locked.** Any decision may change when the code shows it won't work, costs much more than expected, or a simpler option meets the same goal. Follow the change protocol below. Display compatibility decisions (DC1–DC15) live in `05-display-compat-brief-LATER.md`.

## Change protocol

1. Add a row to the **Change log** at the bottom: ID, old, proposed, evidence (`path:line`, measurements), impact on other decisions and phases.
2. Set the decision's status below to `change proposed`.
3. Raise it at the next gate (investigation Gate 1 or 2, or a phase report). Don't implement the change before the owner says "go".
4. Once approved, update the decision text, set status to `changed (date)`, and update any brief, spec or plan section that depends on it.
5. Never change a decision silently.

## Fixed guardrails (not decisions)

Changing these needs the owner's explicit approval in chat, with the reason.

## P11 (2026-11-04, under the owner authorisation above)

Its card is the opaque page colour `#141414` (not transparent) so the disc never sits under card text, and its exported colour stays solid.

## P11b (2026-11-04, under the owner authorisation above)

- All five Looks are packs. None needs T3 or pack CSS for its colours alone (Classy Black could stay a plain Look), but each one's type is a catalog font that loaded from Google Fonts at run time, and a pack is the only thing that bundles a face (G4, D23). Night Glow (gradient frame, gradient numerals, segmented rings, 18 px corners, a navy page), Black and Gold (gradient frame and numerals) and Paper (hex layer, gradient numerals) use T3; Classy Black is the thin Geist face; Liquid Glass is its material and an ambient stage.
- Every sample theme now sets `font` to `auto`, `sans` or `mono`: no sample Look asks a font host for anything (closes L35). A test pins the sample themes; `pack-visibility.spec.ts` logs the requests of each worn pack.
- The per-page backdrop limit (section 9.3: 8) is a static rule in `index.css`: with a pack worn, a blurred card in the ninth zone of the page grid or later fills to the fallback alpha instead. It counts zones, not blurred cards, so a page can only be under the limit; Classic keeps its own blur. The page grid carries `data-page-grid` for it. The studio canvas has no limit (it draws one card per widget being edited).
- Lite mode with a pack worn now draws `backdrop-filter: none` on a blurred card (the P9b rule wrote both the prefixed and the unprefixed declaration and the minifier kept only the prefixed one, which did not override the card's own: the computed value was `blur(0px)`, which keeps a backdrop layer). An engine without `backdrop-filter` fills such a card to the fallback alpha (`@supports not`).
- Black and Gold's gradient on the gauge arcs is not built: it needs a ring fill token and an SVG gradient in the ring primitive, a new T3 name. The sheen is on the frame and the numerals (L90).
- Manrope's vertical metrics are set to 1.0 em ascent and 0.26 em descent (as Space Mono's were): at 1.37 em its label and value boxes overlapped in MenuBar and StreamChat.

## P11b fix round 1 (2026-11-04)

- The per-page backdrop limit (section 9.3: 8) is counted over every layer, not zones: the island and an alert layer reserve one each, so a card blurs in the first 6 zones of the page grid (the kiosk's, and the studio canvas's zones), and the blurs inside a card are off while a pack is worn. It stays a rule for every worn pack, because the selector only matches a blurred card: a pack that does not blur (Term) has nothing to limit, and a test pins that. It is not scoped to Liquid Glass alone because Night Glow blurs too, and a pack added later should not have to say so.
- A pack's chrome (L25) is colours: its surface, text and edge, taken by the island's black tint (the legacy default) and the alert cards. A tint someone chose, and Classic, are unchanged. It carries no blur: the 8 layers reserve one each for the island and an alert.
- `ring-fill` and `spark-fill` are T3 names (Classic `none`), read through `safeGradient` and drawn as an SVG gradient; the loader holds their stops to 3:1 on the surface like `num-fill`.
- Visual items no phase owned (Paper's mono labels and focus outline, `label-case`, Tape '86's stripe bars, the studio-only rows) belong to the post-plan polish backlog (investigation section 11, after P12: owner-scheduled, not a phase and not part of the P0 to P12 goal), not to P12 (the validator and user packs).
- Known gap (P11b fix 2): the page limit of 8 backdrop layers counts blurred cards by class; the InfoPanel panel item's inline `backdropFilter` (`ProfileView.tsx`) is outside it. The pages the specs draw have no panel blur, and a rule that beats inline styles would reach every panel item on every Look. Recorded as L92 in the backlog. The island plus alert reservation is arithmetic: the specs run with no live alert, and alert cards add no blur (`bg-card`).

  1. **A fail-closed grammar** (`src/looks/user-css.ts`, rule `user-css`). Selectors are the `data-part` slots of spec 03 joined by a descendant or child combinator; `:scope` is out, because it matches the pack's overlay as well as its card. A colour is a hex or `rgb()` literal or a `var(--pack-*)` that resolves in the same file, with no fallback, no loop and none of the chrome's own `--pack-chrome-*`; a text or mark colour keeps 0.5 of its alpha through any var. Properties are a short list, each with its own value shape: no filter, blend, mask, text-fill, clip, gradient, font or animation. Shadows stop at 4 px of offset and 12 px of blur with no spread, and the marks (`ring`, `bar`, `meter`, `spark`, `threshold`, `range`, `fader`, `icon`) take no box paint at all: a background on a bar is the colour of its own fill, which no measure can tell from a value. No at-rule. **`url()` is refused outright**, stricter than the row asked: a relative URL in a `<style>` resolves against the page, not the pack folder, so no spelling stays inside the pack without a rewrite, and images are the stage's job. The built-ins' CSS rules are as they were.
  2. **A render check at import** (`src/looks/pack-render-check.ts`, a lazy chunk the studio loads only for a pack with CSS). The candidate is not stored: its files go by message to a hidden same-origin iframe of the Widget QA page (`?widget-qa&pack-check`), through the loader's candidate path (`wearCandidate`, in that frame's own page only), and every template widget is drawn at 1x1, 2x2, 4x2 and 4x4 on the fixture data. `measurePack` (`pack-render-measures.ts`) is the one set of measures, moved out of `pack-visibility` and `pack-selectors`, which now call it; it reads the page with the stylesheet on and off in one task, and `renderRefusals` refuses what only the stylesheet causes: a new visibility or bar problem, a gauge no longer lit, a spark, icon, threshold, range or fader no longer seen, text under 3:1 and worse than without the CSS. No answer in 90 s, a page that cannot be opened or an answer of the wrong shape refuses the pack. The check reads computed paint, so a candidate's fonts and images are not loaded in the frame, and it cannot see pixels: what the grammar leaves possible but only pixels would show (a shadow over a neighbour) is what its caps are for. Text a painted box covers is seen: at each text's centre `elementsFromPoint` must meet the text's element, one around it or one inside it, before an element that paints a background (a transparent wrapper does not count); that is compared with the page without the pack's CSS, because some built-in layouts overlap at the smallest tier (Term's header over the RAM tile). The check draws the widgets on cards only: a pack's rules also reach the widgets inside a panel (`PanelView` puts `data-look` on `.wp-panel` and the items use the same `data-part` slots), on the panel's surface, which is not drawn. That is a stated limit, not covered by the caps. `?widget-qa` stays a debug tool. In a build without debug the server decides on any path whose query carries `widget-qa` (the client mounts the page from the query alone, so `/index.html?widget-qa` and a fallback path count) and opens it only for a request with `Sec-Fetch-Dest: iframe` and `Sec-Fetch-Site: same-origin`, not at all under `USER_PACKS=off`, and the page shows no toolbar, sets no `__qa*` tool and does nothing outside a same-origin parent. Those headers come only to localhost or https, and `crypto.subtle` needs a secure context too, so a pack with CSS cannot be imported from another machine over plain http: the check fails closed there.
  3. **A server-held key** (`crates/ips-server/src/pack_sign.rs`). 32 random bytes made on first signing in `DATA_DIR/pack-signing.key`, owner-only where the platform has modes (on Windows the key inherits the ACL of `DASHBOARD_DATA_DIR`, so that folder must be private to the user), outside the packs folder. No route reads it and nothing exports the data folder (no server route or desktop command copies it wholesale; a test walks the spellings). A keyed BLAKE2b (already in the lock through the Stream Deck, so no new crate) signs the pack id and the SHA-256 of every stored file, in `pack.sig`. `POST /api/packs/<id>/sign` carries the CSS and the hash the studio took of the bytes it checked, behind `X-Dashboard-Pack`, this computer unless `ALLOW_REMOTE_UPLOAD=1`, the request guard, and `USER_PACKS=off`; a hash that is not the stored one is a 409, so a file changed since the check is not signed. `POST /api/packs` still refuses `pack.css`, so an import is the plain files first. Every read hashes the folder again: a `pack.css` with no valid signature, an edit to any file, a file added or removed, a signature copied from another pack, a missing or damaged key (never replaced) all make the folder not a pack: not listed, its files 413, `pack.css` 404. `GET pack.css` gives `Content-Type: text/css`, `nosniff`, `default-src 'none'; sandbox` (L95) and `X-Pack-Signature: valid`; the loader refuses a pack whose CSS comes without that word, and the grammar and `packIssues` run again on what it gets. `pack.json` gives `X-Pack-Css: 1` for such a pack, so the loader asks for `pack.css` only then: a pack with no CSS needs no signature and makes the same requests as before.

  **The threat model, and no more than this.** The check runs in the studio, in the client. The server cannot watch it, so **the signature attests only that a client on an allowed origin claimed a pass for these exact bytes**. It stops a file dropped into `DATA_DIR/packs`, a stored file edited afterwards, CSS copied in from elsewhere and CSS that skipped the flow by accident. **It does not stop a local process that can forge the same-origin request**: anything that can reach the loopback port can send `X-Dashboard-Pack: 1` and no `Origin`, and be signed without any check having run, and anything that can read the data folder can read the key. Nor does it say a pack is safe to share: sharing stays off, and a signature means nothing on another machine. What stands behind a forged signature is the grammar, which the loader runs on every load whatever the signature says: a forged pack can still only be plain paint on the slots, so what it can do is what the render check exists to catch, hide or fade content, not reach outside the pack.
